# DPCO Capability-Centric Architecture
**Мастер-спецификация для реализации в Google AI Studio (PoC-001)**

Данный документ фиксирует итоговую архитектуру интеллектуального слоя (Representation Layer) для системы Deterministic Processing & Cognitive Orchestration (DPCO). 

## 1. Фундаментальная парадигма

Проект совершает переход от **Function-Centric** (маршрутизация по имени функции) к **Capability-Centric** оркестрации.
* **Capability (Возможность):** Абстрактный контракт действия при заданных условиях (например, "пересечение прямых в $\mathbb{R}^2$"). Является первоклассным объектом системы.
* **Executor (Исполнитель):** Конкретная, заменяемая реализация Возможности (аватар).
* **Representation (Представление):** Структурированное, многомерное описание поведения и ограничений Исполнителя, собираемое на основе истории.

## 2. Разделение осей знаний (The 3 Axes of States)

Система строго разделяет юридический контракт, исторический опыт и текущий прогноз.

1. **Capability Status (Контракт):**
   * `DECLARED`: Автор заявил возможность.
   * `QUALIFIED`: Система подтвердила возможность тестами.
2. **Evidence Status (Эпистемология):**
   * `UNOBSERVED`: Нет записей в Ledger.
   * `OBSERVED`: Есть успешные запуски, но без независимой проверки.
   * `VERIFIED`: Запуски подтверждены Независимым Верификатором.
3. **Prediction Status (Эвристика):**
   * `AVAILABLE`: Прогноз для текущей задачи построен с высокой уверенностью.
   * `INSUFFICIENT_DATA`: Данных мало, применяется консервативная стратегия (fallback).
   * `OUT_OF_DOMAIN`: Задача выходит за рамки известных зон стабильности.

## 3. Модель пяти представлений (The Five Views)

Чтобы избежать потери информации, каждый исполнитель описывается в пяти ортогональных проекциях:

1. **API View:** Сигнатуры, схемы I/O, заявленные операции (Статика).
2. **Structure View:** Уровень изоляции (`stdio`/процесс), зависимости, мутабельность (Архитектура).
3. **Behavior View:** $P_{success}$, задержки, распределение ошибок (Статистика из Ledger).
4. **Verification View:** Гарантии детерминизма, методы доказательства (Достоверность).
5. **Context View:** Зоны стабильности, допуски на вырождение, масштабы чисел (Физика).

*Смысл:* Противоречия между этими представлениями (например, API заявляет поддержку, но Behavior показывает 100% сбоев в определенном Context) не схлопываются, а используются движком для корректировки ранжирования.

## 4. Пайплайн интеграции (Safety-First Two-Tier Model)

Интеллектуальный слой (CRE) **не имеет права** обходить детерминированные фильтры ядра. Он выступает как рекомендательная система.

**Поток исполнения:**
1. **Task Arrival:** Поступает `Task` с параметрами и ограничениями.
2. **Deterministic Pre-filtering:** `CapabilityRegistry` выдает список *базово допустимых* кандидатов.
3. **Semantic Encoding:** CRE преобразует задачу в вектор признаков (масштаб, признаки вырождения).
4. **Candidate Ranking (CRE):** CRE многокритериально ранжирует допустимых кандидатов, выдавая `RankedCandidate` с расщепленным `Confidence` (по объему данных и по схожести контекста).
5. **Deterministic Dispatching:** `Dispatcher` берет верхнего кандидата и прогоняет через `ConstraintValidator` и `ContradictionGate`.
6. **Execution & Verification:** Задача выполняется и независимо верифицируется.
7. **Evidence Feedback:** `EvidenceProcessor` (идемпотентно) читает `Execution Ledger` и обновляет `Behavior View` и `Context View`.

## 5. Экспериментальный дизайн PoC-001

Для доказательства превосходства новой архитектуры используется тестовый стенд на 30 задач, разделенных на наборы.

**Исполнители:** `ExactExecutor`, `NumericalExecutor`, `BadExecutor`.
**Тестовая выборка (30 задач):**
* `Training Set (15)`: Для накопления опыта в Ledger.
* `Validation Set (5)`: Для калибровки весов прогнозирования.
* `Test Set (10)`: Чистые задачи для итогового замера (включая численно неустойчивые системы, где $10^{-6}$ радиан).

**Режимы сравнения:**
* **Mode A (Legacy):** Слепая сортировка по стоимости. `Numerical` должен падать на неустойчивых данных.
* **Mode B (Static):** Ранжирование по статичным Views (API, Structure).
* **Mode C (Adaptive):** CRE обучается на `Ledger`. Ожидается, что на Test Set система автоматически переключится на `ExactExecutor` для неустойчивых систем, поняв, что $P_{precision\_loss}$ у `NumericalExecutor` в этом контексте фатален.

## 6. Задачи для реализации в Google AI Studio

1. **Разработка контрактов:** Написать структуры данных (Pydantic) для `CapabilityStatus`, `EvidenceStatus`, `PredictionStatus`, и пяти классов `*View`.
2. **Интерфейсы движка:** Реализовать абстрактные классы `IRepresentationStore`, `IEvidenceProcessor`, `CapabilityRepresentationEngine`.
3. **Модификация Dispatcher:** Обновить метод `dispatch` в `core.py`, чтобы он принимал список `allowed_candidates` и запрашивал их ранжирование у CRE.
4. **Математика прогнозирования:** Реализовать базовую логику вычисления расщепленного `Confidence` и $P_{success}$ без нейросетей (на базе байесовского сглаживания и эвристик расстояния в Context View).
